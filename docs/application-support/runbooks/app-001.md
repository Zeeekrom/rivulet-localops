# APP-001 · API unavailable or degraded

- **Symptom:** internal health reports the `api` component as `degraded` or `unavailable`; smoke requests fail.
- **Impact:** operators cannot reliably diagnose or submit requests. Existing ledger events remain unchanged.
- **Severity:** SEV-2 when all requests fail; SEV-3 for bounded degradation.
- **Detection:** check `/ops/v1/health`, correlation/request IDs in redacted logs, and the post-deploy smoke result.
- **Diagnosis:** separate API process health from ledger, configuration and provider component states. Do not inspect or
  copy request bodies into a support record.
- **Root cause:** determine from allowlisted error category and deployment/configuration change evidence; do not infer it
  from a liveness-only signal.
- **Resolution:** remove the safe fault injection or repair the failed runtime/configuration, then restart through the
  normal deployment mechanism.
- **Rollback:** restore the previously verified immutable image/release if the fault followed a deployment.
- **Verification:** overall health is `healthy`; a bounded diagnose smoke request returns HTTP 200; correlation headers
  and ledger integrity remain valid.
- **Escalation boundary:** escalate when two recovery attempts fail, the ledger is also unavailable, or the issue is in
  the hosting platform rather than the application.
- **Lessons learned:** liveness, readiness and component health must remain separate signals.
