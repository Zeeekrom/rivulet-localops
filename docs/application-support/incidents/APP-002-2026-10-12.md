# APP-002 · Deployment-control and hosted rollback exercise · 2026-10-12

- **Symptom:** candidate health reported `v0.7.2` while verification required `v0.8.0`.
- **Impact:** the local fixture changed nothing. Hosted run `38205693603` then temporarily deployed the valid v0.7.2
  candidate and injected a post-check failure; its automatic rollback command failed before redeployment.
- **Severity:** simulated SEV-2 for the candidate failure; real release-control defect for the failed rollback step.
- **Detection:** release verification produced a deterministic mismatch.
- **Diagnosis:** all other bounded health fields passed, isolating release identity.
- **Root cause:** the local mismatch was deliberate. The hosted rollback defect was an unsupported
  `--no-pretty-print` flag on `az deployment group create`; that flag belongs to the preceding `what-if` command.
- **Resolution:** removed the invalid flag. Safety-recovery run `38205872737` redeployed v0.8.0 and passed all smoke
  checks before a corrected rollback drill was attempted.
- **Rollback:** the workflow redeploys the captured previous image/release through the same Bicep template.
- **Verification:** local recovery passed. Deployment run `38205416715` and safety-recovery run `38205872737` both
  verified v0.8.0. Corrected drill `38206163289` then passed rollback and recovered-release verification. The first
  hosted rollback attempt is retained as a failed experiment, not counted as success.
- **Escalation boundary:** a failed hosted rollback must be escalated rather than hidden by a tag move.
- **Lessons learned:** a rollback path must itself be exercised; a syntactically plausible recovery command is not
  recovery evidence.
