# APP-002 · Detectable deployment failure and rollback

- **Symptom:** post-deploy verification reports wrong release, non-OK health, public-boundary exposure, missing security
  headers or a capability-deny failure.
- **Impact:** the candidate cannot be accepted; the last verified public revision must remain or be restored.
- **Severity:** SEV-2.
- **Detection:** `scripts/verify_public_deployment.py` checks release identity, `/healthz`, six internal boundaries and a
  deny-by-default scenario after the existing Bicep deployment.
- **Diagnosis:** compare the captured pre-deploy health, candidate smoke artifact and immutable image tag.
- **Root cause:** classify as image/release mismatch, runtime health, boundary regression or capability-control failure.
- **Resolution:** the existing `deploy-azure` workflow redeploys the previously observed image and release through the
  same Bicep template.
- **Rollback:** never invent a tag; fail closed if no previous image/release was captured. A synthetic drill can force a
  failure only after all real candidate checks pass.
- **Verification:** rerun the full smoke suite against the restored release and retain all three JSON artifacts.
- **Escalation boundary:** escalate if rollback verification fails or the Azure control plane cannot redeploy the prior
  image. Do not delete revisions or force-push tags.
- **Lessons learned:** a successful deployment command is not a successful release; acceptance depends on observable
  application behaviour and release identity.
